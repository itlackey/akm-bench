# `harbor/treatment-library` — the D6 cold-start library

**This is the akm treatment arm's benchmark library, not the P0 smoke
fixture.** For the smoke fixture (a 15-asset plumbing check used by
`p0-smoke.yaml`), see `harbor/seed-library/README.md`.

## What it is

26 hand-authored assets of **generic software-engineering practice** —
systematic debugging, test workflows, git operations, build systems, Linux
CLI fluency, environment troubleshooting, incremental-change discipline,
patch/diff mechanics, non-interactive command hygiene, verifying against a
task's stated acceptance criteria, and reading unfamiliar codebases — in
the akm 0.9 bundle layout (`skills/<name>/SKILL.md`, `knowledge/*.md`,
`lessons/*.md`). It is the cold-start knowledge base the akm treatment arm
carries into terminal-bench 2.x and SWE-bench Verified trials, per D6 in
`docs/plans/benchmark-harness-decisions.md`.

**Consolidated from an earlier 35-asset draft** (an adversarial review
found the same procedure independently authored two or three times —
bisect, incremental-change, codebase-orientation, single-test-running,
port-triage, build-failure-triage — each such cluster co-ranking for every
matching query and spending the agent's context three times on one idea).
Every duplicate cluster is now ONE asset; the unique value of each twin was
merged in rather than dropped. Net effect: fewer files, denser and more
useful content per file, and zero co-ranking noise on any query that used
to return 2-3 near-duplicate hits — verified below. See "Why no
`commands/`" for why that type was retired entirely rather than merely
thinned.

See `docs/harbor-p0.md`'s "D6 treatment library" section for the full asset
inventory, the indexing facts that drove how these were authored, and the
hermetic verification methodology.

## Provenance

Hand-authored for this benchmark, from general software-engineering
knowledge — not derived from, copied from, or fitted to either benchmark
corpus. Nothing here was generated by importing real repository
documentation, mining benchmark train splits, or reading any SWE-bench or
terminal-bench task definition.

## Contamination policy

- **No SWE-bench Verified repo names or specifics.** No mentions of
  `django`, `sympy`, `astropy`, `flask`, `requests`, `matplotlib`,
  `xarray`, `pytest` internals-as-subject, or any other repo the corpus
  draws from — pytest/jest/go-test/cargo-test are referenced only as
  *generic tools*, the same way any engineer would use them, never in a
  way that assumes or reveals a specific task's fixture.
- **No terminal-bench task content.** No task-shaped scenarios, no
  fixture data, no phrasing lifted from or resembling an actual
  terminal-bench 2.x task instruction.
- **Explicitly rejected alternatives (D6):** per-domain `akm import` of
  real repo docs for SWE-bench instances (task leakage), and
  learned-from-train-split content (needs an in-container LLM engine;
  revisit once D1's `evolve` arm exists — the two share machinery).

## The D6 caveat

This bundle's quality **caps the measurable treatment effect**. A weak or
narrow library produces a null result that says nothing about akm's
retrieval/curation mechanism itself — authoring effort here is not
overhead, it *is* the experiment. If a future A/B run shows no effect, the
first question is whether this library was good enough to matter before
concluding anything about akm.

## Asset shape

Every asset carries frontmatter with a sharp `description` (≤250 chars,
written as the literal search target — what an agent mid-task would type),
`tags` (short exact-match tokens), and — critically — `searchHints`
(realistic paraphrases and query variants, including ordinary connector
words like "in"/"not"/"only"). Knowledge assets additionally carry dense
H2/H3 headings that carry the same key terms.

This is not a style preference; it follows directly from how akm indexes:

- akm's FTS and embeddings index **only** `name` / `description` / `tags`
  / `searchHints` (+ `examples`/`usage`) / headings — **never full body
  prose** (verified against `src/indexer/search/search-fields.ts`:
  body-only terms return zero hits).
- Heading (`toc`) indexing only happens for the `knowledge` asset type
  (`src/core/adapter/adapters/akm-metadata.ts` — the TOC contributor is
  keyed to the `knowledge-md` renderer only). A heading inside a
  `SKILL.md` or a command template is real, useful prose once the agent
  opens the asset, but contributes nothing to search recall — those
  types lean on frontmatter instead.
- `keywords:` in frontmatter is **not indexed** — only `tags:` is
  (`applyCuratedFrontmatter` reads `fmData.tags`, no `keywords` alias).
  `harbor/seed-library/`'s assets use `keywords:` and get zero benefit
  from it; this bundle uses `tags:` throughout.
- A literal `$1`, `$2`, `$3`, or `$ARGUMENTS` anywhere in a `.md` file's
  body — even inside a fenced shell example — flips its classification to
  `command` (`COMMAND_PLACEHOLDER_RE` in `src/indexer/walk/matchers.ts`
  scans full content). This bit one asset during authoring (an awk
  cheat-sheet using `$1`/`$2`/`$3`) and was fixed by rewriting the
  examples (`knowledge/sed-awk-jq-xargs-recipes.md` still carries the
  workaround — reverting it to the more idiomatic `$1`/`$2`/`$3` form would
  reintroduce the exact misclassification this note describes, since this
  repo does not own akm's indexer source to fix the regex itself). No
  asset in this bundle now uses `$1`/`$2`/`$3`/`$ARGUMENTS` at all — grep
  the tree to confirm before adding a new one.
- akm's own FTS matching is an implicit AND over every query token with
  no stopword removal — a natural-language query only matches if *every*
  word in it (including "in", "not", "only") appears somewhere in the
  entry's indexed row. `searchHints` is the field built for absorbing
  this: use it to spell out realistic full phrasings, not just keywords.

## Why no `commands/`

The akm 0.9 bundle layout supports a `commands/` type (slash-command
templates using `$ARGUMENTS`), and an earlier draft of this library used it
for seven assets. In THIS harness that type is dead weight: a Harbor trial
agent never types a slash command, so a `commands/` asset is reachable only
as prose through `akm_search`/`akm_show`, exactly like `knowledge/` — with
one difference that matters for retrieval. Heading (`toc`) indexing only
happens for the `knowledge` type
(`src/core/adapter/adapters/akm-metadata.ts`); a heading inside a
`commands/` template contributes nothing to search recall. Every asset that
used to live under `commands/` was therefore either merged into its
`knowledge/` twin (where one already existed) or converted to a
standalone `knowledge/` asset (where its content was unique) — never left
as `commands/`. The type is retired from this bundle, not merely thinned;
`derive_seed_expectations()` reports no `command` floor for this library,
and a test pins that.

## Verification

Verified with a real `akm` 0.9.1 binary in a hermetic bundle (fresh
`AKM_BUNDLE_DIR`/`AKM_CONFIG_DIR`/`AKM_DATA_DIR`/`AKM_CACHE_DIR`/
`AKM_STATE_DIR`, `AKM_FORCE_INIT_TMP_STASH=1`), seeded with the exact merge
semantics `AkmOpenCode._build_seed_bundle_command()` uses in-container
(`akm bundle create --set-default`, `cp -a` each type subdirectory onto the
scaffolded bundle root, `akm index --full`). Current result: **38 total
entries (26 authored + 12 of akm's own `facts/conventions/*` scaffold)**.
`akm info` byType:

| type | count |
|---|---|
| `knowledge` | 20 |
| `skill` | 3 |
| `lesson` | 3 |

(No `command`, `agent`, or `script` — see "Why no `commands/`" above.)

Re-run against the CURRENT tree with a fresh battery (not drawn from these
assets' own `searchHints`, so this is a real recall measurement, not a
tautology):

- Every one of the 26 assets is independently reachable via
  `akm search "<type>/" --format json` prefix enumeration (20 + 3 + 3 =
  26, matching the byType table).
- Every duplicate-topic cluster from the pre-consolidation draft (bisect,
  incremental-change, codebase-orientation, single-test-running,
  port-triage, build-failure-triage) now resolves cleanly to its one
  surviving asset at rank 1, with no competing near-duplicate hit.
- The four coverage gaps an adversarial review found zero-hit against the
  pre-consolidation draft — concrete Python exception vocabulary
  (`ModuleNotFoundError`, `ImportError`, relative-import errors), patch/diff
  mechanics (`git apply` failures, unified diffs), non-interactive command
  hygiene (pagers, `apt` prompts, hanging commands), and verifying against
  a task's stated acceptance criteria — now each resolve to their own
  purpose-built asset at rank 1 against realistic phrasings.
- `akm feedback <ref> --positive` (the mutating call path self-check probe
  5 exercises) exits 0 against a live ref from the current bundle.
- Grepped the current tree for the SWE-bench/terminal-bench contamination
  policy below: zero hits.

The AND-semantics floor documented in "Natural-language recall" below is
real and not fully closeable by hints (a query using a word no asset
claims, e.g. "best"/"way", still zero-hits) — this is expected FTS
behavior, not a defect, and is the reason `searchHints` should keep
absorbing realistic phrasings as the library grows rather than being
treated as a one-time pass.

## Usage

Pass `seed_library_dir=harbor/treatment-library` as a job kwarg on the akm
arms to seed this bundle instead of the default. `harbor/seed-library/`
remains the default for `p0-smoke.yaml` and other plumbing-only jobs — this
bundle is deliberately not used there (D6).

The install-time self-check is parameterized to whichever seed library the
job configures, so pointing `seed_library_dir` here is supported:
`derive_seed_expectations()` computes the per-type floors from this
directory (`knowledge>=20`, `skill>=3`, `lesson>=3` — no
`agent`/`script`/`command` requirement), and probe 5 sends `akm feedback`
to a ref taken from probe 3's own enumeration of the live bundle rather
than to a named fixture asset. Verified end to end against a real akm
0.9.1 index of both this bundle and `harbor/seed-library/`: all of probes
2–5 pass for each.

### Natural-language recall

*(Historical measurement, from the pre-consolidation 35-asset draft — the
practice it established, writing `searchHints` as whole questions, carries
forward unchanged to the current 26-asset library and is re-verified above
against the current tree.)*

akm's FTS is an implicit AND over every query token with no stopword
removal, so a full-sentence query only matches an asset whose indexed row
contains *every* word in it — connector words included. Keyword-shaped
queries always retrieved well here, but the first measurement of
natural-language phrasings (`how do I run only one test`, `why does my
test pass locally but fail in ci`, ...) returned **zero hits on 8 of 8**:
`do` appeared in only 3 of the 35 assets, `I` in 5, `what` in none.

Every asset therefore also carries two or three `searchHints` written as
whole questions, not just keyword variants. Re-measured after adding them,
on the same hermetic bundle:

| probe | before | after |
|---|---|---|
| 8 natural-language phrasings, intended asset at rank 1 | 0/8 | 7/8 |
| 16 independent keyword queries, intended asset at rank 1 | 12/16 | 16/16 |
| assets whose indexed row contains `do` / `I` / `what` | 3 / 5 / 0 | 29 / 34 / 24 |

The residual miss (`what is the best way to debug a failing build`) turns
on `best` and `way`, which no asset claims — an honest floor of AND
semantics rather than a gap a hint can close. Keep this property in mind
when adding an asset: **write at least one hint the way a stuck agent
would actually type the question.** Per D6 this ceiling caps the
measurable treatment effect.
